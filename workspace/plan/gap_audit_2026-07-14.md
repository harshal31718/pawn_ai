## D. Browser test findings (live)

### D-1 `[fixed — verify live]` Sidebar kebab menu turns translucent while open (user screenshot: garbled overlapping items)
User screenshot (project "suiiiii" → chat "New Chat" → kebab): dropdown items
rendered garbled/overlapping the rows beneath. Root cause: the kebab wrapper
divs use `opacity-0 group-hover:opacity-100 transition-opacity` — when the
pointer leaves the row (or hovers a *different* row's kebab) while the menu is
still open, the whole wrapper (including the OPEN menu, which is its child)
fades toward opacity 0, so the underlying sidebar rows bleed through the
"transparent" menu. Fixed: added `focus-within:opacity-100` to all three
wrappers (ProjectRow ×2 — project + in-project chat rows; Sidebar ×1 —
standalone chat rows): the kebab button keeps focus while its menu is open, so
an open menu now always renders fully opaque. Verify live in Chrome.
Note: `animate-in fade-in zoom-in-95` classes on the dropdown are dead (no
tailwind animate plugin installed) — harmless, but could be removed or the
plugin added if the entrance animation is actually wanted.

## F-8 `[fixed]` F-1 root cause found and fixed: unguarded `resolver.pick()` peek in `agent/graph.py`
User ran `docker compose logs backend --tail 100` and pasted the traceback:
`NoEndpointError: All endpoints for 'gemini-2.5-flash' are rate-limited or
inactive.`, raised from `final_node`'s `candidates = resolver.pick(model_id,
user_id=user_id)`, uncaught. That call exists only to grab a provider name
for a cosmetic `final_provider` UI event — the real, failover-safe call is
`normalize.chat_stream` right below it, which tries every endpoint of every
fallback model via `resolver.fallback_models(model_id, ...)`. The peek only
checks `model_id`'s own endpoints (a strict subset), so it could raise on a
model chat_stream would likely have failed over away from successfully. Same
unguarded pattern existed in `direct_answer_node`. Both fixed: degrade to
`"unknown"` on `(ProviderError, NoEndpointError)` instead of crashing;
`chat_stream`'s own switch callbacks correct the badge once a real endpoint
is found. Also: `routes/chat.py` gained a dedicated `except NoEndpointError`
branch (it isn't a `ProviderError` subclass, so it was falling into the
generic catch-all) for the residual genuinely-fully-exhausted case, now
surfacing an honest message instead of "unexpected error." Committed as
`ea765df`. This confirms the original F-1 hypothesis's second branch ("a real
bug in the new-graph final path under total exhaustion") — it was that, not
genuine unrecoverable exhaustion.

## F-9 `[fixed]` Full pytest gate's real root cause: SQLite checkpointer contention on the Windows bind mount, not a langchain-core sandbox artifact
User ran `docker compose build backend && docker compose exec backend pytest
-n auto` for real. Result: 16 failed, ALL `sqlite3.OperationalError: unable
to open database file` on every test that invokes `/chat` — a completely
different failure mode than the sandbox's 15 langchain-core-version-related
failures (D-2), which this session's earlier audit incorrectly assumed would
just be "expected green in Docker." Root cause: every `/chat`-touching test
module's `client` fixture (`with TestClient(app) as c:`) runs the real
FastAPI lifespan, which opens a real `AsyncSqliteSaver` against
`CHECKPOINTS_DB` = `/app/data/checkpoints.db` — `/app/data` is
`docker-compose.yml`'s bind mount of `./backend/data` from the Windows host.
`pytest -n auto` (mandated by `testing.md`) runs many parallel xdist worker
processes, all hitting that one file concurrently — SQLite + Docker Desktop
for Windows bind mounts are a known bad combination for file locking. Fixed:
`tests/conftest.py` now sets `PAWN_DATA_DIR` to a throwaway directory unique
per xdist worker (`PYTEST_XDIST_WORKER`), before any `app.*` module import —
same established pattern as the file's existing `JWT_SECRET`/
`ENCRYPTION_SECRET` overrides. Verified safe: `registry.loader.load_registry`
self-heals via `seed_registry()`. Committed as `ea765df`. **Not yet
re-verified against real Docker** — needs the user to re-run the gate.
